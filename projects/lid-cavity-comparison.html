Lid-Driven Cavity Solver Comparison

A multi-language CFD benchmark for the 2D incompressible lid-driven cavity problem, comparing the same numerical study across MATLAB/Octave, Python, C, C++, OpenMP, MPI, and a CUDA prototype path.

Problem

The lid-driven cavity is a compact CFD benchmark for incompressible flow, pressure-velocity coupling, convection-scheme behavior, mesh effects, and validation against published centerline velocity data. The challenge here was not only solving one case, but keeping the benchmark consistent across several programming languages and parallelization approaches.

Benchmark setup

Physics

2D incompressible cavity with a moving top lid, no-slip side and bottom walls, and Reynolds-number based test cases.

Study matrix

N = 32, 64, 128; Re = 100, 400, 1000; upwind and central convection schemes; RBGS and RBSOR pressure solvers.

Implementations

MATLAB/Octave, Python/NumPy, C, C++, OpenMP, MPI, and CUDA prototype path, with shared CSV-oriented comparison outputs.

My contribution

  • Structured the project as a solver-comparison portfolio instead of a single isolated CFD code.
  • Kept cases matched by grid size, Reynolds number, convection scheme, and pressure solver so comparisons are meaningful.
  • Separated serial baselines, OpenMP versions, MPI case-level parallelism, and CUDA prototype work.
  • Prepared comparison scripts and reporting outputs for runtime, residuals, validation behavior, and completion status.
  • Documented incomplete solver groups transparently instead of hiding unfinished runs.

What the numbers show

  • Eight CPU solver groups completed the full 36-case benchmark set.
  • The fastest complete group was c_openmp_t4 with a reported median runtime of 236.76 s.
  • The next fastest complete group was cpp_openmp_t4 with a reported median runtime of 284.40 s.
  • Serial C/C++ implementations were much faster than Python and Octave vectorized workflows for the collected benchmark cases.
  • MPI in this project represents case-level parameter-study distribution, not CFD domain decomposition.

Why this project matters

This project shows the full engineering workflow: physics, numerical method, implementation, automation, HPC execution, validation, runtime comparison, and honest limitations. It is stronger than a single solver because it explains how the same CFD problem behaves when the implementation language and parallelization strategy change.

Limitations and next steps

  • The solvers are educational and portfolio solvers, not production CFD packages.
  • The MPI implementations distribute cases rather than decomposing the spatial domain.
  • Future work should add OpenFOAM comparison, stronger automated report generation, and a compact summary table for validation error versus runtime.
